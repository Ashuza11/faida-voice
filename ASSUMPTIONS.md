## `lib/nlu/numbers.ts` — minimal verified word list (2026-08-12)

A research agent searched for Kinyarwanda numeral and money vocabulary before implementation. Rather than encode the full grammar it found (which included unverified/inferred rules), `parseKinyarwandaNumber` only covers the subset that is independently source-verified — everything else correctly falls through to `null` (→ `UNKNOWN`, per §5).

**Shipped (high confidence — cross-checked against real Rwandan franc banknote naming on Wikipedia, and matches CLAUDE.md §5's own worked examples):**
- Digits 0–10: `zeru, rimwe, kabiri, gatatu, kane, gatanu, gatandatu, karindwi, umunani, icyenda, icumi` — cross-confirmed by [ELIAS/Harvard](https://elias.fas.harvard.edu/unit-grammar/cardinal-and-ordinal-numbers), [Omniglot](https://www.omniglot.com/language/numbers/kinyarwanda.htm), [languagesandnumbers.com](https://www.languagesandnumbers.com/how-to-count-in-kinyarwanda/en/kin/).
- `ijana` = 100, `igihumbi` = 1000, `magana atanu` = 500, `ibihumbi bibiri` = 2000, `ibihumbi bitanu` = 5000 — all verified against real denomination names in [Wikipedia's Rwandan franc article](https://en.wikipedia.org/wiki/Rwandan_franc).
- Spelling note: one source spelled 8 as "umunani", another as "umunane" — went with "umunani" (majority of sources); flag if a native speaker says otherwise.

**Explicitly NOT shipped — needs native-speaker input before it can be built:**
- **Noun-class agreement.** Kinyarwanda numerals 1–7 change form depending on the noun class of what they modify (e.g. "two" appears as babiri/ibiri/ebyiri/bibiri in different contexts). The pattern behind `magana atanu`/`ibihumbi bibiri` (numeral root loses its "ga-" prefix and takes an "a-" or "bi-" prefix depending on scale) is only inferred from three currency examples, not confirmed by a grammar source. Building this out as a generative rule without confirmation risks silently mis-parsing amounts — unacceptable for money.
- **Tens 40–90** (e.g. "mirongo ine" for 40) — only single-sourced, not cross-verified.
- **Compound numbers** (1500, 12000, etc.) and how they're joined ("na"/"n'") — constructed from a pattern, not found written verbatim anywhere.
- **Informal spoken shortcuts.** No source describes how vendors actually abbreviate prices when speaking casually (dropping "amafaranga", saying bare digits, rounding, code-switching). This is the highest-risk gap for a money-critical parser, since it's exactly the input distribution real speech will produce, and it can only be closed with real vendor recordings/transcripts or native-speaker input — not further web research.

**Next step to unblock:** get a native Kinyarwanda speaker (or real transcribed vendor phrases) to (a) confirm/correct the noun-class prefix rules and tens 40–90, and (b) supply real example sale/debt/payment sentences for `fixtures/utterances.rw.json`, which is still empty for exactly this reason.

## LLM entity-extraction fallback — explicit deviation from §5 (2026-08-12)

CLAUDE.md §5 says Kinyarwanda numerals are parsed deterministically, "not by an LLM." The user explicitly asked to add an LLM-based fallback anyway, after I flagged this tension and recommended staying fully deterministic (Google STT for transcript only, `classify.ts` unchanged). Per the working agreement ("say so once... then follow it anyway"), this is built — but scoped as narrowly as possible to keep the parts §5 actually cares about (money, numerals) untouched:

- **`lib/nlu/extract-llm.ts`'s `extractEntities` only resolves *which* known product/customer a transcript refers to.** It is called only when `classify.ts`'s deterministic substring matcher finds zero or ambiguous (multiple) matches — the usual cause is an ASR transcription error mangling a name, not a grammar problem. It is never given the job of parsing a quantity or amount; `findKinyarwandaNumber` (fully deterministic, unit-tested) remains the only numeral parser in the codebase.
- **Kind is never LLM-decided.** The caller always supplies which of SALE/DEBT/PAYMENT/SAVING is being recorded (chosen by tap, per §6) before extraction runs.
- **Money arithmetic is never computed by the LLM.** Whatever product/customer `extractEntities` resolves gets fed into the same `assemble*` functions in `lib/nlu/classify.ts` that the deterministic path uses — `qty × unitPrice` is always that one piece of code, regardless of which path resolved the entities. This is the reason `classify.ts` was refactored to expose `assembleSale`/`assembleDebt`/`assemblePayment`/`assembleSaving` before this module was written.
- **Product/customer names are constrained to the vendor's real catalog, not free text.** The Zod schema passed to Claude only allows `z.enum(realProductNames).nullable()` (and same for customers) — the model cannot return a name that isn't already in that vendor's Dexie-stored product/customer list; anything else is `null`.
- **Verified, not assumed, how that constraint is actually enforced.** Inspected the real output of the Anthropic SDK's `zodOutputFormat()` helper directly (`node -e "console.log(JSON.stringify(zodOutputFormat(schema)))"`) rather than trusting the docs' framing. Finding: the JSON Schema sent to the API does **not** contain a real `enum` keyword — the SDK currently downgrades `z.enum(...)` to `{type: "string", description: "{enum: [...]}"}`, since Anthropic's structured-output API doesn't support `enum` server-side yet. So the model is only *steered* toward the catalog via a description hint, not hard-blocked from hallucinating a name at generation time. The actual enforcement is client-side and after the fact: the SDK's returned `.parse(content)` re-validates the raw JSON against the *original* Zod schema (`zodObject.safeParse`, see `node_modules/@anthropic-ai/sdk/helpers/zod.js`) and throws on anything not in the enum. `extractEntities` catches that throw and returns `null` for the field, and additionally re-checks the parsed value against the real name list before returning it (`productNames.includes(...)`) as a second, independent guard. Net effect: a hallucinated name cannot reach the caller, but it does cost one wasted (thrown-away) model call rather than being prevented outright — worth revisiting if a future SDK version adds real server-side `enum` support.
- **Every failure mode degrades to `{productName: null, customerName: null}`, never throws.** Missing `ANTHROPIC_API_KEY`, network failure, model refusal, or a schema-validation throw are all caught in `extractEntities` and treated identically — the caller always falls back to tap/`UNKNOWN`, consistent with the project's "never guess, never partially write" rule for money-adjacent code.
- **Not integration-tested against the real Anthropic API** — only unit-tested against a mocked `messages.parse`, per CLAUDE.md §7's "spike messily first" guidance for third-party APIs (an LLM call is nondeterministic and costs money; not something to gate CI on). `ANTHROPIC_API_KEY` is not yet set in `.env.local` — this module is built and tested but has not yet made a real API call.
- **`lib/nlu/extract-llm.ts` imports `zod/v4`, not the project-wide `zod` (v3 classic) import used everywhere else** (`lib/nlu/intent.ts`, `lib/sync/schema.ts`, etc.) — required because the Anthropic SDK's `zodOutputFormat` helper is typed against `zod/v4`'s `ZodType`. This is a one-file exception, noted inline in the file itself; nowhere else in the codebase should switch to `zod/v4`.
